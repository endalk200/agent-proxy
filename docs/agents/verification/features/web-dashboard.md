# Web dashboard

The daemon serves the built dashboard on its own listener (from source, the web client's build directory; the compiled binary serves the copy embedded in it), beside `/api/` and the proxy routes: the usage Dashboard at `/` and Accounts at `/accounts`, moved between without reloading and keeping the search params. It is a sidebar app shell built from shadcn/ui components in the dark-only "Doom 64" theme (red primary, green, blue selection, small rounded corners, Oxanium and Source Code Pro, both shipped in the build), with roomy cards and tables. Wherever a provider is named, its own mark goes with it: Claude's orange spark, and OpenAI's blossom for Codex in the text colour. The sidebar holds the daemon switcher ("This Mac" and the daemon's address, with address, version and build, uptime and Copy address), Dashboard, Accounts with a red badge counting accounts that need sign-in, a pool strip saying who gets each pool's new sessions, and Connect clients. The Dashboard shows what went through the proxy over a range the owner picks (6h, 24h, 7d by default, 30d, 90d, Custom calendar days, or Lifetime, kept in the address): a KPI row (Requests with success rate, Tokens split by token kind, Cache hit rate, Equivalent cost with any unpriced models flagged, each with a sparkline), a Token trend stacked by model, in equivalent cost or tokens, then Accounts beside Models, each a donut of its share of tokens or equivalent cost beside a legend (or a table), then every account's limit windows; every chart animates in and springs to new numbers (snapping instead under reduced motion); it updates live as requests finish and limit windows change. The Accounts page shows one table per pool, headed by which account gets new sessions, and each row's priority, label with its plan badge and email, status with when it was last used, one column per limit window (% left, when it resets, a bar of the share left coloured by how much is left), enabled switch and an actions menu; Refresh limits reads fresh limit windows for every account. With no accounts, `/` and `/accounts` show a three-step first-run guide whose first step adds a Claude or Codex account. The page follows the daemon live through its event stream (`GET /api/events`): a change the daemon makes or the CLI makes, such as a cooldown starting or ending, a sign-in expiring, or an account disabled, added, removed or renamed, shows at once without reloading; the row flashes in its new status colour and a notice in the corner says what happened, while the sidebar badge and pool strip follow. When the daemon stops answering, a banner says so, pointing at `agent-proxy daemon status` for why, and the page keeps the last reported state, dimmed and read-only, until the daemon answers again; the stream reconnects by itself, to a restarted daemon too when it comes back at the same address. Connect clients is a dialog with the three `agent-proxy connect` commands and the proxy key, masked until revealed, each with a copy button. The owner manages accounts from the page: drag a row by its priority badge (or press the arrow keys on it) to reorder, flip the enabled switch, double-click a label to rename it, and remove an account from its actions menu after a confirmation. Every change goes through the daemon API and shows at once; a change the daemon refuses shows a notice in the corner and the page goes back to what the daemon holds. Add account (the page header, or the first-run guide) opens a sign-in dialog: pick Claude or Codex, the daemon starts a login and the provider's sign-in page opens in a new tab while the dialog waits, or the owner pastes the callback URL instead; on success the dialog shows the email and plan with an editable label, and the account joins the bottom of its pool. Sign in again, on an account that needs it (its row's status or its sheet's status card), runs the same login for that account, which returns to Active in place. A sign-in made in the dialog gets no live notice, as the dialog says how it went. Closing the dialog while it waits cancels the login in the daemon. Clicking a row slides in the account sheet from the right: a status card, Overview (the account's limit windows with a Refresh button, its last 7 days through the proxy, priority with move up and down, enabled, details, the pool order, remove) and an Activity tab marked Planned. Planned pages are hidden.

## Sub-features

- `dashboard-served` answers `GET /`, `/accounts` and other page paths with the dashboard's `index.html` (`no-cache`) and `/assets/*` with immutable caching; an asset the build lacks, or a path outside it, is a 404; with no build found, `/` says to run `bun run build`.
- `dashboard-pages` shows the usage Dashboard (heading `Dashboard`) at `/` and Accounts (heading `Accounts`) at `/accounts`; the sidebar's links `Dashboard` and `Accounts` move between them without reloading, keep the search params (`/?range=30d` → `/accounts?range=30d`), mark the current one `aria-current="page"`, and focus its heading; a reload or a pasted link opens the same page.
- `dashboard-clean-load` loads with HTTP 200, title `agent-proxy`, no console errors and no page errors.
- `dashboard-pools` shows on Accounts a region per pool with a table `"<Provider> accounts"` in priority order: priority, label with its plan badge (with a `New sessions` pill on the account that gets them) and email, status (`Active` or `Disabled` with `Used <4 min ago|yesterday|…>` or `Never used` beneath it, `Cooling down` with `until <time> · in <countdown>` beneath it, ticking each second, `Needs sign-in` with button `Sign in again to <label>`, or `Unknown` for a status this build does not know, the rest of the list unaffected), one column per limit window (see `dashboard-limit-cells`), switch `"<label> enabled"`, and button `"Actions for <label>"`; the region's heading, above the table's box rather than inside it, reads `New sessions go to <label>` (then ` · then <label>, <label>` naming the other Active accounts in the order new sessions would go to them: by priority, then the most headroom), `No account can take new sessions` (with ` · next reset <time> (in <countdown>)` while any account is cooling down, and a note: `Every account in the <Provider> pool hit its plan's limit. … when the first cooldown ends, at <time>.` when all are, `Every enabled <Provider> account is cooling down or needs sign-in. …` when some need sign-in, else `Every enabled <Provider> account needs sign-in, …`), or `Every <Provider> account is disabled`.
- `dashboard-logo` shows the project mark in the browser tab and the sidebar, including the collapsed rail and mobile drawer.
- `dashboard-sidebar` shows link `Dashboard` first, then link `Accounts` with `<n> need(s) sign-in` when any account does, else the account count; and a `Pools` list whose items are named `<Provider>: new sessions go to <label>`, `…: no account can take new sessions until <time>` (showing `Back in <countdown>`) while a cooldown runs, `…: no account can take new sessions` (showing `Unavailable`), or `…: every account is disabled`.
- `dashboard-switcher` opens a popover titled `Running` (or `Can't reach the daemon`) with Address, Version (`v<version> (<build>)`: `(source)` from source, the binary's commit when compiled) and Uptime, and a `Copy address` button that copies `http://<address>`.
- `dashboard-first-run` shows, under heading `Get started` at `/` (under `Accounts` at `/accounts`), a `Get started` list (`Add an account` with buttons `Add a Claude account` and `Add a Codex account`, each opening the sign-in dialog for that provider; `Connect your clients` with the three commands and the proxy key; `Add a fallback`) while the daemon holds no accounts.
- `dashboard-add-account` opens dialog `Add an account` from the page header's `Add account` button (shown once the daemon holds an account; disabled while it is unreachable): buttons `Claude` and `Codex`, each with its plans and the clients that use it. Picking one starts a login (`POST /api/logins`), opens its authorize URL in a new tab, and shows dialog `Sign in to <Provider>` with `Waiting for you to sign in…`, a link `Open sign-in page again`, `Choose another provider`, and `Cancel`; the dialog polls the login every second. When the provider's redirect reaches the daemon, it shows dialog `<Provider> account added`: the email, `Signed in · Active`, the plan, `It joins the <Provider> pool at priority <n> of <n>. …` (or `It's the first account in the <Provider> pool, …`), and textbox `Label` holding the daemon's suggestion; `Done`, Enter, or closing the dialog saves an edited label (`PATCH /api/accounts/:id`), and the table shows the account at the bottom of its pool. Signing in to an account the daemon already holds updates it instead: `<label> is signed in again`, no label field.
- `dashboard-paste-callback` opens, from button `Paste the callback URL instead` (`aria-expanded`), the sign-in URL with `Copy sign-in URL`, the redirect address it returns to (`http://localhost:<port>/callback` for Claude, `http://127.0.0.1:<port>/auth/callback` for Codex), and textbox `Callback URL` with `Continue` (`Checking…` while the daemon answers). A URL the daemon refuses shows its message as an alert under the field (`That is not a URL. …`, `That URL belongs to another <Provider> sign-in, not the one in progress.`, `That URL has no authorization code in it.`) and the login keeps waiting; an accepted one ends as the redirect does.
- `dashboard-sign-in-again` runs the login from button `Sign in again to <label>` in the row, or `Sign in again` in the sheet's status card, as dialog `Sign in again to <label>` (`Sign in as <email> to put it back in the <Provider> pool.`), with no provider to pick. Signing in as that account shows `<label> is signed in again` / `It's back in the <Provider> pool at priority <n>.`, and the row and the open sheet turn Active in place, with no new row. Signing in as another account adds it instead, saying `You signed in as <email>, not <email>, so it was added as a new account. <label> still needs sign-in.`
- `dashboard-sign-in-cancel` cancels the login in the daemon (`DELETE /api/logins/:id`, so its callback port stops listening) when the dialog closes while the login starts or waits: `Cancel`, `Close`, Escape, a click outside, or `Choose another provider`.
- `dashboard-sign-in-errors` shows an alert in the dialog, with `Try again` starting a new login: `Couldn't start the sign-in` and the daemon's message (409 when the callback port is taken: `Could not listen on 127.0.0.1:<port> …`, with a hint to finish or cancel the other sign-in); `The sign-in failed` and the daemon's reason (the provider denied access, the exchange failed); `The sign-in timed out` (10 minutes); `The sign-in was cancelled` (another sign-in for the provider took its place); `The sign-in was lost` (the daemon no longer knows it, as after a restart). While the daemon does not answer a poll, the waiting card says `Can't reach the daemon. … Still waiting.` When the browser blocks the new tab, a callout `Your browser blocked the new tab.` offers link `Open sign-in page`.
- `dashboard-connect-clients` opens dialog `Connect clients` with `agent-proxy connect claude-code`, `codex` and `opencode`, each with `Copy <command>`, the pools each client spends, and the proxy key masked as its first 6 characters, 16 dots and its last 4; `Reveal` shows it whole and `Hide` masks it again; `Copy proxy key` copies it. A copy button is named `Copied` for a moment after it copies.
- `dashboard-live` shows each change made outside the page within a second, without reloading: the row's `data-flash` names its new status for about 2.6 seconds while it flashes (amber `cooling-down`, red `needs-sign-in`, green `active`, grey `disabled`; a steady tint with reduced motion), and a notice (region `Notifications`) titled `<label> is cooling down` (`It hit its plan's limit. agent-proxy skips it until <time>.`), `<label> is back` (`Its cooldown ended, so it's in the <Provider> pool again.`), `<label> needs sign-in`, `<label> is signed in again`, `<label> was turned off`, `<label> was turned on`, `<label> was added` (`It joins the <Provider> pool at priority <n>.`), `<label> was removed`, or `<old> is now <new>`. A move gets no notice (the order shows it), nor does a `pools-changed` event, which the daemon sends when only the order new sessions go in changed (accounts sharing a priority trading places as their headroom moves): the header, `New sessions` pill and pool strip follow it quietly. Last used updates quietly as accounts serve requests (the daemon records it at most once a minute), and a change made on this page, including a sign-in through its dialog, gets neither notice nor flash. The sidebar badge, pool strip, pool headers and countdowns follow.
- `dashboard-unreachable` shows a status banner `Can't reach the daemon at <address>. Run agent-proxy daemon status to see why, or agent-proxy daemon start to start it.` within a second of the daemon stopping (within about 20 seconds when it stops answering without closing the connection, such as when suspended), keeps the tables and pool strip as last reported, dims them, disables every actions menu, and shows `Unreachable` in the switcher; it clears within about a second of the daemon answering again, and the page shows what the daemon holds then. A daemon that answers with an error shows `The daemon answered with an error.` and its message.
- `dashboard-reorder` moves an account when its handle, button `Reorder <label>` (the priority badge, with a grip on hover), is dragged or gets ArrowUp/ArrowDown. Rows stay put while dragging: dropped near the top or bottom edge of a priority's rows, the account takes a priority of its own there (an accent line marks the gap); dropped across a row's middle, it shares that row's priority (its rows are outlined). The pool's header reads `Drop to move to priority <n>`, `Drop to share priority <n> with <labels>`, or `Drop on an account to share its priority, or between priorities to move` where a drop would change nothing (onto its own priority or either side of a priority it holds alone). Each arrow key press moves one step: an account alone at its priority shares the next one over, and an account sharing a priority takes that side of it alone; nothing happens past either end. Escape cancels a drag. The daemon's priorities change (`accounts --json`), the header's `New sessions go to …` follows, and a hidden live region says `<label> moved to priority <n> of <m>.` or `<label> now shares priority <n> with <labels>.` Accounts sharing a priority show the same number, their badges joined by a rail and no line between their rows.
- `dashboard-toggle` flips switch `"<label> enabled"` (no longer read-only): the account turns Disabled or back, and who gets new sessions follows.
- `dashboard-rename` turns a double-clicked label (button `<label>`, also Rename in the actions menu or the sheet) into textbox `Label for <label>`; Enter or leaving it saves the trimmed label, Escape, an unchanged label or a blank one keeps the old.
- `dashboard-row-menu` offers `Open details`, `Rename`, `Refresh limits` (reads that account's limit windows, see `dashboard-refresh-limits`), `Move up`, `Move down` (one step each, as the arrow keys; disabled at their end of the pool), `Share priority with`, a submenu of each other priority by its number and the labels holding it (disabled when every account already shares its priority), and `Remove…`.
- `dashboard-remove` asks in alertdialog `Remove <label>?` (email, who gets new sessions next, a warning when no other account in the pool is enabled) with `Cancel` and `Remove account`; confirming removes the account and focus goes to the `Accounts` heading.
- `dashboard-sheet` opens dialog `<label>` when a row (or its label button, `aria-expanded`) is clicked: crumb `<Provider> pool / <n>th priority`, `Close details`, title with `Rename`, email and plan, region `Status` (`Cooling down until <time>`, `It hit its plan's limit. agent-proxy skips it until the limit resets.` and the countdown, `Gets every new … session.`, `Gets new … sessions while it has more room left in its limits than <labels>, at the same priority.`, `Shares priority <n> with <label>, which has more room left in its limits, so it gets new sessions first.`, `Ready. Takes new sessions when <label> can't.`, `Sign in again` when it needs sign-in, `Enable` when disabled), tabs `Overview` and `Activity Planned`; Overview opens with region `Limit windows` (`As of <age> ago`, button `Refresh`, and a row per window of the pool's columns: `<window> <n>% left` or `Used up`, a larger bar, `Resets in <countdown> · <time>` with the weekday a day or more away, and ` · As of <time> (<age> ago)` when older than an hour; `Not on the <plan> plan` for a window it lacks; `Not read yet. …` before any is read), then region `Last 7 days through the proxy` (tiles Requests with `<n>% success`, Tokens with `<n>% cache hit rate`, Equivalent cost with `At API list prices` or `<n> model(s) unpriced`, and a chart of tokens per day named `Tokens per day: Wed 0, Thu 1.2M, …` over today and the 6 days before), then Priority `<n> of <m> in the <Provider> pool` with `Move up`/`Move down`, switch `Enabled`, Plan, Email, Last used, Added, list `<Provider> pool order`, and `Remove…`. Clicking another row swaps it; Escape, `Close details` or a click elsewhere closes it, handing focus back to the row's label button (except after a click elsewhere). On screens 1280px and wider the page makes room for it. It stays readable but its controls disable while the daemon is unreachable.
- `dashboard-change-errors` shows a notice (region `Notifications`) when a change fails: `Couldn't <disable|enable|rename|move|remove> <label>` with `The daemon no longer holds <label>. It was removed, perhaps from the CLI.` for a 404, `Can't reach the daemon. …` when it is down, else the daemon's own message; removing an account already gone says `<label> was already removed`.
- `dashboard-range` shows group `Range` with buttons `6h`, `24h`, `7d`, `30d`, `90d`, `Custom` and `Lifetime`, the current one `aria-pressed="true"`; 7d is the default and leaves the address bare, any other is `?range=<key>`. `Custom` opens popover `Custom range` with date fields `From` and `To` (to today at most) and `Apply`, giving `?range=custom&from=YYYY-MM-DD&to=YYYY-MM-DD` (both days included) and naming the button `Nov 9 – Nov 10`. Every `/api/usage/*` call carries the range and `tz=<the browser's IANA zone>`. A missing or malformed range reads as 7d.
- `dashboard-kpis` shows regions `Requests` (`<n>`, `<n.n>% success` or `— success`, `<n> failed · <n> limited · <n> incomplete`), `Tokens` (total, a bar split by token kind, `Uncached input`, `Cache read`, `Cache write`, `Output`, and `Output includes <n> reasoning` when any), `Cache hit rate` (`<n.n>%` or `—`, `<n> read from cache of <n> input`) and `Equivalent cost` (`$<n>`, `<$0.01` for a sliver, `At API list prices; your plans are flat.`, and `<n> model(s) unpriced` naming them on hover or focus), each with a sparkline named `<KPI> over <the range in words>` and a hover tooltip; numbers read 1,284 under 10,000, then 12.9K, 4.83M, 1.24B.
- `dashboard-trend` shows region `Token trend` (`Equivalent cost|Tokens per <15 minutes|hour|3 hours|6 hours|day> by model, <range>`): group `Measure token trend in` picks `Cost` (the default; priced models only) or `Tokens`, kept in the address as `?metric=tokens`; list `Models` as its legend, then stacked columns by model, each model in its own fixed colour whatever its rank. With five or more models it names the three largest and adds the rest up as `Other` (a neutral grey; its legend item reads `Other <n> models` and names them on hover); four models are all named. Hovering a column, or focusing the chart and pressing ArrowLeft/ArrowRight (Home, End), shows a tooltip `<total> <bucket> <value> <model> …`, the total `$<cost>` or `<n> tokens`; buttons `Chart`/`Table` switch it to table `Token trend by model` (one row per bucket with any, the same columns as the legend). With none: `No priced usage in <range>.` or `No tokens in <range>.`
- `dashboard-breakdowns` shows region `Accounts` beside region `Models`, each with group `Measure accounts|models in` (`Tokens`, the default, or `Cost`) and group `Show accounts|models as` (`Chart`, the default, or `Table`), headed `Share of tokens|equivalent cost, <range>`. Chart shows a donut named `<Accounts|Models> by tokens|equivalent cost: <name> <n.n>%, …` with the total in its hole (hovering a slice or legend entry dims the rest and puts its share, name and value there), beside (below, in a narrow card) list `<Accounts|Models> by tokens|equivalent cost`: one entry per slice, largest first, reading `<name> <value> <n>%`. At most six slices: past five, the rest fold into a grey `Other (<n>)` that names them on hover. A model keeps its trend colour; an account keeps its own colour whatever its rank, priority or pool order, and through other accounts' removal, and one no longer held is grey. In Cost, rows with no list price are left out of the donut, named under the legend as `Left out, with no known list price: <names>.`, and an account whose cost leaves out an unpriced model's tokens shows its cost with a `*` and is named as `Partly left out: <labels>.`; with nothing priced the card says `No priced usage in <range>.` Table shows table `Accounts|Models` with every row, largest first by the measure: Account (with Requests where the card has room) or Model, Tokens, Equivalent cost (`Unpriced` for a model with no list price, a `*` when partly so), Share (`—` for an unpriced row in Cost). An account the daemon no longer holds reads by its last label with a `Removed` tag (its email on hover), or `Removed account` when the daemon never knew its name; clicking an account's legend entry or row opens its sheet. With none: `No requests in <range>.`
- `dashboard-limit-windows` shows region `Limit windows` with link `Accounts` and one table, `"Limit windows"`, headed `Account` and a column per window id any account reports, ordered `5-hour`, `Weekly`, per-model weeklies (`Fable weekly`), `Monthly`; 5-hour and Weekly always have columns. A row per account, pool by pool in priority order, shows its provider's mark beside its name (which opens its sheet); a column its provider has no such window for stays blank, while `—` means a window not read yet.
- `dashboard-limit-cells` shows each window as `<n>% left` (rounded down, or `Used up` with none left) on the left and `resets in <countdown>` on the right over a full-width bar as long as the share left: green above 50% left, amber from 50% down to 20%, red below 20%, and with none left an empty bar on a red track; `—` for a window the account lacks. Numbers whose `as of` is over an hour old dim and take a tab stop, and on hover or focus say `As of <time> (<age> ago)`. An account cooling down keeps its red track beside `Cooling down`.
- `dashboard-refresh-limits` reads fresh limit windows (`POST /api/limits/refresh`): button `Refresh limits` in the Accounts header for every account (disabled with a spinner while it reads), `Refresh limits` in a row's actions menu or `Refresh` in the sheet for one; the bars update when it answers, and a failure shows notice `Couldn't refresh limits` with the daemon's message. Disabled while the daemon is unreachable.
- `dashboard-limit-resets` badges each account row beside its plan with the count of its limit resets (none for 0; `data-tone="warn"` when one expires within 7 days), and the account sheet's section `Limit resets` lists them soonest first: name, `Refills <windows>`, `expires <day> (in <countdown>)` (warn tone within 7 days), and button `Redeem <name>`, or the provider's reason (`Not usable right now` without one) in its place; `None now. New ones show up here by themselves.` when it holds none. A Codex account whose limits say `canBuyReset` gets link `Buy a reset` to `https://chatgpt.com/codex/purchase/reset` (new tab).
- `dashboard-redeem` asks in alertdialog `Redeem <name>?` (the windows it refills with `<n>% used` or `not read yet` and a meter, the provider's side effect, `A redeem can't be undone.`) with `Cancel` and `Redeem` (`Redeeming…` while it runs); the outcome shows in the sheet: `Redeemed <name>` (success), `<name> wasn't redeemed` or `Not sure <name> was redeemed` (warning) with the daemon's message, `Not sure <name> was redeemed` too when the daemon gives no answer in 150 seconds, or `Couldn't redeem <name>` (error) with the daemon's refusal (404, 409). The badge and list follow the answer and `limits-changed`.
- `dashboard-usage-live` follows `usage-recorded` and `limits-changed` on the event stream: the KPIs refetch at most once a second, the trend and breakdowns at most every 15 seconds (once for a burst), limit bars move as soon as the event arrives, and the header's `Live · last request <n>s ago` (`Live · no requests yet` before any; `Offline` while the daemon is unreachable) pulses. A stream that reconnects reloads the limit windows and usage.
- `dashboard-narrow` lays the Dashboard out by width: KPIs 4 across from 1280px of window, 2 × 2 below, one column on phones, with Token trend across the page and Accounts beside Models only from 1280px, stacked below (a breakdown's donut sits beside its legend when the card is 30rem wide or more, above it otherwise); a card's controls drop under its title on phones, the range presets scroll within their own box on the narrowest phones, and the limit-window table scrolls sideways inside its card rather than overlapping. Each Accounts table lays out by its own card's width, not the window's: under 40rem (a phone, or beside the open sheet on most screens) it shows priority, account, status and actions only (the sheet keeps the limit windows and the Enabled switch); under 54rem it also shows the limit windows; wider, it adds the Enabled switch and the blank columns that line a pool's windows up with a wider pool's. Plan and `New sessions` badges wrap under a label that has no room for them, and a limit-window cell puts its reset under its percent when narrow. From 1280px of window the page makes room for the open sheet. The sidebar folds to an icon rail with its toggle (or Cmd/Ctrl+B), remembered across reloads; below 768px it is a drawer behind the top bar's toggle, which closes when a link in it is followed and hands focus to the new page's heading. A row's `Sign in again` sits beside its status on wide tables and under it on narrow ones. Dialogs stay within the window, scrolling inside when it is short; the sign-in dialog keeps every control inside a 390px screen, stacking the callback field over `Continue`.

## How to get to it (user POV)

- Open the daemon's address (`agent-proxy daemon status` prints it; `http://127.0.0.1:8318/` by default) in a browser for the Dashboard, or `/accounts` for Accounts; add `?range=24h` (or `custom&from=…&to=…`) for a range.
- Open an account's sheet and click `Redeem <name>` under `Limit resets`, or `Buy a reset` on a Codex account offered one.
- Click `Dashboard` or `Accounts` in the sidebar; pick a range in group `Range`; click `Refresh limits` on Accounts or in a row's actions menu, or `Refresh` in an account sheet.
- Send requests through the proxy (see [Claude proxy](./claude-proxy.md) and [Codex proxy](./codex-proxy.md)) with the Dashboard open.
- Click `Add account`, or `Add a Claude account` / `Add a Codex account` in the first-run guide, or `Sign in again` on an account that needs it, then sign in at the provider in the new tab, or paste the URL that tab was redirected to.
- In development, `bun run dev` (or `verify web --dev`) serves the dashboard with hot reload, and `vite preview` (or `verify web`) serves the build; both pass `/api/` to the daemon named in `$XDG_STATE_HOME/agent-proxy/daemon.json`.

## Driving it with verify

Preconditions:

- `verify doctor` is all `ok`. `bun run build` has run, so the daemon finds the dashboard.
- Accounts are seeded as in [Accounts](./accounts.md) → Seeded list (Work 1 Active, Personal Max 2 Needs sign-in, Spare 3 Disabled), and `verify cli -- daemon start` exits `0`.
- `verify web` has printed a URL; `verify doctor` includes `web build fresh`.

- **Load.** Run `verify browse /` and `verify browse /accounts`. Each exits `0`; `status 200`, `title agent-proxy`, `console 0 error(s)`, `pageerror 0`; the first has heading `Dashboard`, the second `Accounts`.
- **Dashboard, empty.** Read `/`'s `.aria.yml`. Link `Dashboard` is current; group `Range` has `7d` pressed; region `Requests` reads `0` and `— success`; region `Token trend` reads `No priced usage in the last 7 days.`; region `Limit windows` has table `Limit windows` with columns `Account`, `5-hour` and `Weekly` and `—` in each cell (nothing read yet); `Live · no requests yet`.
- **Dashboard, live.** With the Dashboard open on the daemon's own address, send one Claude message through the proxy as in the [Claude proxy](./claude-proxy.md) drive (its fake API answers with usage). ## Gotchas

- `verify web` and `verify browse` drive Vite's server, which passes `/api/` to the sandbox's daemon through its state file; with no daemon running, the page shows the unreachable banner, not an error. Driving the daemon's own address is the user's path.
- Live updates come from the event stream, not a poll: a change made from the CLI shows within a second. The page checks the daemon's info every 15 seconds only to notice a daemon gone silent, so a suspended daemon takes up to 20 seconds to show as unreachable.
- A change made on the page gets no notice or flash, by design: look for notices only after changes made elsewhere (the CLI, another tab, the daemon itself).
- The refused-change notices (`Couldn't disable Home` after a CLI removal) need the page not to have heard of the removal yet, which the live stream makes a matter of milliseconds; component tests cover them, and a drive rarely can.
- The event stream reconnects to the same address only. The sandbox's `listen = "127.0.0.1:0"` gives a restarted daemon a new port unless you pin it (see Unreachable).
- The Dashboard's KPIs refetch at most once a second after a request finishes, but the trend, Models and Accounts cards wait up to 15 seconds after their last load: wait before calling a chart stale. A burst of requests costs one refetch each.
- Usage is asked in the browser's time zone (`tz=`), so calendar days, day buckets and Custom ranges follow the machine running the browser, not the daemon's.
- Limit-window numbers dim after an hour by their own `as of`; a fresh sandbox has none until a request or a refresh reads them, so every cell reads `—`.
- A flash lasts about 2.6 seconds and the notices 6 (10 for Needs sign-in); screenshot at once.
- Drag by the priority badge, not the row: the row itself opens the sheet. Drags follow the row under the pointer, so they need no particular speed or distance.
- `verify web` serves a build. After editing anything the build reads (`apps/web/src`, `index.html`, `vite.config.ts`, `daemon-proxy.ts`, the package's `package.json` or `tsconfig.json`), doctor reports `web build fresh` as `FAIL` until `verify web --restart`. The daemon reads the build at request time, so after `bun run build` a reload shows it without restarting the daemon.
- The daemon looks for the build at `dist/web` beside its bundle (`apps/cli/dist/web`, copied there by the CLI build), then at `apps/web/dist` when it runs from source.
- The sign-in dialog opens the provider's page with `window.open`; a browser tool that blocks pop-ups shows `Your browser blocked the new tab.` instead, which is the intended fallback. Playwright gets the tab as a `popup` event.
- Claude's and Codex's real callback ports (54545, 1455) are fixed; set `"callbackPort":0` in `AGENT_PROXY_PROVIDER_ENDPOINTS` so a run never collides with another daemon's or `codex login`'s sign-in.
- A live sign-in to the owner's real Claude or ChatGPT account needs the owner at the browser; the fake providers stand in for it in every unattended drive.
- Clipboard reads need permission in the browser tool (`clipboard-read`, `clipboard-write`); `127.0.0.1` counts as a secure context, so writes work without HTTPS.
- In dev mode the page loads React Refresh scripts, so compare accessibility trees rather than raw HTML between modes.
