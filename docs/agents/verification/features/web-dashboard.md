# Web dashboard

The daemon serves the built dashboard at `/` on its own listener, beside `/api/` and the proxy routes. It is a sidebar app shell in a dense console style, light or dark from the system setting. The sidebar holds the daemon switcher ("This Mac" and the daemon's address, with address, version, uptime and Copy address), Accounts with a red badge counting accounts that need sign-in, a pool strip saying who gets each pool's new sessions, and Connect clients. The Accounts page shows one table per pool, headed by which account gets new sessions, and each row's priority, label and email, plan badge, status, last used, enabled switch and an actions menu. With no accounts it shows a three-step first-run guide. The page follows the daemon live through its event stream (`GET /api/events`): a change the daemon makes or the CLI makes, such as a cooldown starting or ending, a sign-in expiring, or an account disabled, added, removed or renamed, shows at once without reloading; the row flashes in its new status colour and a notice in the corner says what happened, while the sidebar badge and pool strip follow. When the daemon stops answering, a banner says so and the page keeps the last reported state, dimmed and read-only, until the daemon answers again; the stream reconnects by itself, to a restarted daemon too when it comes back at the same address. Connect clients is a dialog with the three `agent-proxy connect` commands and the proxy key, masked until revealed, each with a copy button. The owner manages accounts from the page: drag a row by its priority badge (or press the arrow keys on it) to reorder, flip the enabled switch, double-click a label to rename it, and remove an account from its actions menu after a confirmation. Every change goes through the daemon API and shows at once; a change the daemon refuses shows a notice in the corner and the page goes back to what the daemon holds. Clicking a row slides in the account sheet from the right: a status card, Overview (priority with move up and down, enabled, details, the pool order, remove) and Activity and Usage tabs marked Planned. Planned pages are hidden.

## Sub-features

- `dashboard-served` answers `GET /` with the dashboard's `index.html` (`no-cache`) and `/assets/*` with immutable caching; any other path the build lacks, or one outside it, is a 404; with no build found, `/` says to run `bun run build`.
- `dashboard-clean-load` loads with HTTP 200, title `agent-proxy`, no console errors and no page errors.
- `dashboard-pools` shows a region per pool with a table `"<Provider> accounts"` in priority order: priority, label (with a `New sessions` pill on the account that gets them), email, plan, status (`Active`, `Cooling down` with `until <time> · in <countdown>` beneath it, ticking each second, `Needs sign-in`, `Disabled`, or `Unknown` for a status this build does not know, the rest of the list unaffected), last used (`Never`, `4 min ago`, `yesterday`, …), switch `"<label> enabled"`, and button `"Actions for <label>"`; the region's header reads `New sessions go to <label>`, `No account can take new sessions` (with ` · next reset <time> (in <countdown>)` while any account is cooling down, and a note: `Every account in the <Provider> pool hit its plan's limit. … when the first cooldown ends, at <time>.` when all are, `Every enabled <Provider> account is cooling down or needs sign-in. …` when some need sign-in, else `Every enabled <Provider> account needs sign-in, …`), or `Every <Provider> account is disabled`.
- `dashboard-sidebar` shows link `Accounts` with `<n> need(s) sign-in` when any account does, else the account count; and a `Pools` list whose items are named `<Provider>: new sessions go to <label>`, `…: no account can take new sessions until <time>` (showing `Back in <countdown>`) while a cooldown runs, `…: no account can take new sessions` (showing `Unavailable`), or `…: every account is disabled`.
- `dashboard-switcher` opens a popover titled `Running` (or `Can't reach the daemon`) with Address, Version and Uptime, and a `Copy address` button that copies `http://<address>`.
- `dashboard-first-run` shows a `Get started` list (`Add an account` with `agent-proxy accounts add claude`, `Connect your clients` with the three commands and the proxy key, `Add a fallback`) while the daemon holds no accounts.
- `dashboard-connect-clients` opens dialog `Connect clients` with `agent-proxy connect claude-code`, `codex` and `opencode`, each with `Copy <command>`, the pools each client spends, and the proxy key masked as its first 6 characters, 16 dots and its last 4; `Reveal` shows it whole and `Hide` masks it again; `Copy proxy key` copies it. A copy button is named `Copied` for a moment after it copies.
- `dashboard-live` shows each change made outside the page within a second, without reloading: the row's `data-flash` names its new status for about 2.6 seconds while it flashes (amber `cooling-down`, red `needs-sign-in`, green `active`, grey `disabled`; a steady tint with reduced motion), and a notice (region `Notifications`) titled `<label> is cooling down` (`It hit its plan's limit. agent-proxy skips it until <time>.`), `<label> is back` (`Its cooldown ended, so it's in the <Provider> pool again.`), `<label> needs sign-in`, `<label> is signed in again`, `<label> was turned off`, `<label> was turned on`, `<label> was added` (`It joins the <Provider> pool at priority <n>.`), `<label> was removed`, or `<old> is now <new>`. A move gets no notice (the order shows it), and a change made on this page gets neither notice nor flash. The sidebar badge, pool strip, pool headers and countdowns follow.
- `dashboard-unreachable` shows a status banner `Can't reach the daemon at <address>.` within a second of the daemon stopping (within about 20 seconds when it stops answering without closing the connection, such as when suspended), keeps the tables and pool strip as last reported, dims them, disables every actions menu, and shows `Unreachable` in the switcher; it clears within about a second of the daemon answering again, and the page shows what the daemon holds then. A daemon that answers with an error shows `The daemon answered with an error.` and its message.
- `dashboard-reorder` moves an account when its handle, button `Reorder <label>` (the priority badge, with a grip on hover), is dragged onto another row or gets ArrowUp/ArrowDown; rows follow the pointer while dragging, Escape cancels a drag, and dropping where it began changes nothing. The daemon's priorities change (`accounts --json`), the header's `New sessions go to …` follows, and a hidden live region says `<label> moved to priority <n> of <m>.`
- `dashboard-toggle` flips switch `"<label> enabled"` (no longer read-only): the account turns Disabled or back, and who gets new sessions follows.
- `dashboard-rename` turns a double-clicked label (button `<label>`, also Rename in the actions menu or the sheet) into textbox `Label for <label>`; Enter or leaving it saves the trimmed label, Escape, an unchanged label or a blank one keeps the old.
- `dashboard-row-menu` offers `Open details`, `Rename`, `Move up`, `Move down` (each disabled at its end of the pool) and `Remove…`.
- `dashboard-remove` asks in alertdialog `Remove <label>?` (email, who gets new sessions next, a warning when no other account in the pool is enabled) with `Cancel` and `Remove account`; confirming removes the account and focus goes to the `Accounts` heading.
- `dashboard-sheet` opens dialog `<label>` when a row (or its label button, `aria-expanded`) is clicked: crumb `<Provider> pool / <n>th priority`, `Close details`, title with `Rename`, email and plan, region `Status` (`Cooling down until <time>`, `It hit its plan's limit. agent-proxy skips it until the limit resets.` and the countdown, `Gets every new … session.`, `Ready. Takes new sessions when <label> can't.`, the `agent-proxy accounts add claude` command when it needs sign-in, `Enable` when disabled), tabs `Overview`, `Activity Planned`, `Usage Planned`; Overview lists Priority `<n> of <m> in the <Provider> pool` with `Move up`/`Move down`, switch `Enabled`, Plan, Email, Last used, Added, list `<Provider> pool order`, and `Remove…`. Clicking another row swaps it; Escape, `Close details` or a click elsewhere closes it, handing focus back to the row's label button (except after a click elsewhere). On screens 1280px and wider the page makes room for it. It stays readable but its controls disable while the daemon is unreachable.
- `dashboard-change-errors` shows a notice (region `Notifications`) when a change fails: `Couldn't <disable|enable|rename|move|remove> <label>` with `The daemon no longer holds <label>. It was removed, perhaps from the CLI.` for a 404, `Can't reach the daemon. …` when it is down, else the daemon's own message; removing an account already gone says `<label> was already removed`.
- `dashboard-narrow` drops the tables' Last used column first, then Plan, then (on phones) Enabled, and folds the sidebar into an icon rail whose items keep their names.

## How to get to it (user POV)

- Open the daemon's address (`agent-proxy daemon status` prints it; `http://127.0.0.1:8318/` by default) in a browser.
- In development, `bun run dev` (or `verify web --dev`) serves the dashboard with hot reload, and `vite preview` (or `verify web`) serves the build; both pass `/api/` to the daemon named in `$XDG_STATE_HOME/agent-proxy/daemon.json`.

## Driving it with verify

Preconditions:

- `verify doctor` is all `ok`. `bun run build` has run, so the daemon finds the dashboard.
- Accounts are seeded as in [Accounts](./accounts.md) → Seeded list (Work 1 Active, Personal Max 2 Needs sign-in, Spare 3 Disabled), and `verify cli -- daemon start` exits `0`.
- `verify web` has printed a URL; `verify doctor` includes `web build fresh`.

- **Load.** Run `verify browse /`. Exit `0`; `status 200`, `title agent-proxy`, `console 0 error(s)`, `pageerror 0`.
- **Codex pool.** With a Codex account added as in the [accounts](./accounts.md) Codex sign-in drive (label `Work`, `carol@example.com`, `Pro`) beside the seeded Claude accounts, run `verify browse /`. The accessibility tree has a region `Codex` after `Claude`, reading `New sessions go to Work`, with table `Codex accounts` holding that account (`Pro`, `Active`), and the `Pools` list has `Codex: new sessions go to Work`.
- **Pools and sidebar.** Read the saved `.aria.yml`. It has `navigation "Dashboard"` with `link "Accounts 1 needs sign-in"` and `listitem "Claude: new sessions go to Work"`; `region "Claude"` with `paragraph: New sessions go to Work` and `table "Claude accounts"` whose rows read `1 Work New sessions me@work.example Max 20x Active …`, `2 Personal Max me@home.example Max 5x Needs sign-in …`, `3 Spare spare@example.com Pro Disabled …`; `switch "Work enabled" [checked]` and `switch "Spare enabled"` unchecked.
- **Served by the daemon.** With your browser tool, open the daemon's own address from `verify cli -- daemon status`. Same page, status 200. `verify shell -- -c 'curl -s -o /dev/null -w "%{http_code}\n" "$(bun apps/cli/src/bin.ts daemon status --json | grep -o "http://[^\"]*")/assets/missing.js"'` prints `404`.
- **Connect clients.** In the browser tool, click button `Connect clients`. Dialog `Connect clients` lists the three commands; the text labelled `Proxy key` is masked and differs from `verify cli -- key`'s output; after `Reveal` it equals it. `Copy proxy key` turns into `Copied`, and the clipboard holds the key.
- **Switcher.** Click button `This Mac <address>`. A popover titled `Running` shows the address, `v0.0.0` and an uptime; `Copy address` copies `http://<address>`.
- **Unreachable.** With the page open, run `verify cli -- daemon stop`. Within a second a status banner reads `Can't reach the daemon at <address>. … This is what it last reported …`; the Claude table is still there, dimmed; `Actions for Work` is disabled; the switcher reads `Unreachable`. Pin the port first so a restart comes back at the same address: `verify shell -- -c 'echo "listen = \"$(bun apps/cli/src/bin.ts daemon status --json | grep -o "127.0.0.1:[0-9]*")\"" > "$XDG_CONFIG_HOME/agent-proxy/config.toml"'` before stopping. `verify cli -- daemon start` again: the banner clears within a second, without reloading, and `verify cli -- accounts disable Work` then shows live as in Live updates. (Without the pinned port the new daemon gets a new one: reload the page at its new address.)
- **First run.** Move the seeded files aside (`verify shell -- -c 'mv "$XDG_DATA_HOME/agent-proxy/accounts" "$TMPDIR/aside"'`) and reload. `list "Get started"` shows the three steps and `agent-proxy accounts add claude`; there is no table and no Pools list. Move the files back.
- **Manage.** On the daemon's own address, with your browser tool, and after each step run `verify cli -- accounts --json` (wait for it: the page asks the daemon again at once, the CLI is the second view):
  - Hover `Reorder Spare`, press the mouse, move onto Work's row, release. Spare is priority 1 (still Disabled), the header still reads `New sessions go to Work`. Focus `Reorder Spare` and press ArrowDown twice: back to 3, focus stays on the handle.
  - Click `Work enabled`: Work is `disabled`, the header reads `No account can take new sessions` (Personal Max needs sign-in). Click it again.
  - Double-click `Personal Max`, type `Home`, press Enter: the label is `Home` in the table and the CLI.
  - Click Spare's email: dialog `Spare` slides in with `3 of 3 in the Claude pool` and status `Disabled … Enable`. Click Work's row: the same sheet now shows `Work`, `Gets every new Claude session.`. Press Escape: the sheet closes and focus is on button `Work`.
  - Open Spare's sheet, click `Remove…`, then `Remove account` in `Remove Spare?`: the sheet closes, the row is gone, and `accounts --json` lists two accounts.

Within a second both pages show Work `Cooling down until <time> · in 2m`, an amber flash (`data-flash="cooling-down"`), the notice `Work is cooling down`, and `New sessions go to Personal Max`.   - Within about 80 seconds of starting the daemon, the credential keeper's refused refresh shows: notice `Personal Max needs sign-in`, a red flash, and link `Accounts 1 needs sign-in`. Screenshot both.
  - When Work's 150 seconds end: notice `Work is back`, a green flash, `New sessions go to Work`, with no request sent. Screenshot both.
  - `verify shell -- -c 'curl -sN --max-time 2 "$(bun apps/cli/src/bin.ts daemon status --json | grep -o "http://[^\"]*")/api/events"'` prints `retry: 1000`, then `data: {"type":"snapshot","accounts":[…],"pools":[…]}`.

## Gotchas

- `verify web` and `verify browse` drive Vite's server, which passes `/api/` to the sandbox's daemon through its state file; with no daemon running, the page shows the unreachable banner, not an error. Driving the daemon's own address is the user's path.
- Live updates come from the event stream, not a poll: a change made from the CLI shows within a second. The page checks the daemon's info every 15 seconds only to notice a daemon gone silent, so a suspended daemon takes up to 20 seconds to show as unreachable.
- A change made on the page gets no notice or flash, by design: look for notices only after changes made elsewhere (the CLI, another tab, the daemon itself).
- The refused-change notices (`Couldn't disable Home` after a CLI removal) need the page not to have heard of the removal yet, which the live stream makes a matter of milliseconds; component tests cover them, and a drive rarely can.
- The event stream reconnects to the same address only. The sandbox's `listen = "127.0.0.1:0"` gives a restarted daemon a new port unless you pin it (see Unreachable).
- A flash lasts about 2.6 seconds and the notices 6 (10 for Needs sign-in); screenshot at once.
- Drag by the priority badge, not the row: the row itself opens the sheet. Drags follow the row under the pointer, so they need no particular speed or distance.
- `verify web` serves a build. After editing anything the build reads (`apps/web/src`, `index.html`, `vite.config.ts`, `daemon-proxy.ts`, the package's `package.json` or `tsconfig.json`), doctor reports `web build fresh` as `FAIL` until `verify web --restart`. The daemon reads the build at request time, so after `bun run build` a reload shows it without restarting the daemon.
- The daemon looks for the build at `dist/web` beside its bundle (`apps/cli/dist/web`, copied there by the CLI build), then at `apps/web/dist` when it runs from source.
- Clipboard reads need permission in the browser tool (`clipboard-read`, `clipboard-write`); `127.0.0.1` counts as a secure context, so writes work without HTTPS.
- In dev mode the page loads React Refresh scripts, so compare accessibility trees rather than raw HTML between modes.
