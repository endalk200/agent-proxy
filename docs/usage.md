# Usage and limit windows

The dashboard's home page shows what went through the proxy over a range you pick (6 hours to lifetime, or two calendar days of your choosing): requests and how many succeeded, tokens by kind (uncached input, cache read, cache write and output, with reasoning counted in output), the cache hit rate, and the equivalent cost, which is what the same usage would have cost at the providers' API list prices (a write to Claude's 1-hour cache at twice the input price). A model with no known price is listed as unpriced and left out of that cost. Breakdowns by model and by account, and every account's limit windows, sit below.

The daemon records one row per Claude message and Codex response in `$XDG_DATA_HOME/agent-proxy/usage.sqlite`, readable only by you, and keeps every row ([ADR-0009](adr/0009-usage-is-recorded-per-request-in-a-sqlite-file-the-daemon-owns.md)). Token counts are the provider's own, read from a copy of each response as it streams to the client, which still gets the provider's bytes unchanged. A request that fails, hits a limit, or ends early because its client went away is recorded too, with the tokens seen so far. A removed account's usage stays in the totals, under the name it had when you removed it. If the file cannot be opened, or a newer build wrote it, the daemon still proxies: it records nothing, logs why, and the dashboard shows the reason instead of usage. It never migrates the file back to an older schema.

Limit windows are Claude's 5-hour, weekly and per-model weekly (such as Fable) windows, and Codex's 5-hour and weekly ones: how much of each is used and when it resets. The daemon reads them from the headers of every answer, and from each provider's usage endpoint at startup, when you add an account, every 30 minutes, just after a window resets, and when you click **Refresh limits**. It reads one account at a time, skips accounts that need sign-in or are disabled, and waits as long as a provider asks (up to an hour) after a 429. When a read fails, the last-known numbers stay, and the dashboard dims any older than an hour. The last-known windows are kept in the same file, so a restarted daemon still shows them.

### Seats that pay for each request

Some Claude seats, such as an Enterprise organization's usage-based seats, have no 5-hour or weekly window: the organization pays for each request, up to a monthly spend limit its admins set. The account's plan reads `Enterprise · usage-based`, and its only limit window is its spend limit, in the **Monthly** column, which shows the money spent this month against the limit, such as `$1.26 of $40`, and resets on the 1st (UTC). The daemon reads the spend only from Claude's usage endpoint, at the times above, because an answer's headers give it only as a rounded share. What Claude answers once the limit is spent has not been seen yet: if it is a 429 that marks the limit rejected with a reset time, as Claude's other limits are, the account cools down until then (the month's end); any other 429 cools it down only for its `Retry-After`, and any other error reaches the client as it is. These requests cost real money, so give such an account a lower priority than your subscriptions: it then takes new sessions only when they are all cooling down or need sign-in. An account added before this release shows plan `Enterprise` until you sign in to it again.

## Limit resets

A limit reset is a single-use grant from the provider that refills some of an account's limit windows early: Claude's free full and Fable resets, and Codex's banked resets from promotions and referrals. They expire if nobody redeems them. The daemon reads each account's limit resets with its windows, at the same times and from the same requests (for Codex, one more request to its list of limit resets, which also says whether the account may buy one), and keeps them in the same file. The dashboard badges each account row with how many it holds, in the warning tone when one expires within 7 days, and the account sheet lists them. The CLI lists them with `agent-proxy accounts resets` ([Manage accounts](accounts.md)).

You redeem one, from the account sheet or with `agent-proxy accounts redeem`; the daemon never redeems one on its own ([ADR-0010](adr/0010-limit-resets-are-redeemed-only-at-the-owners-command.md)). Both ask first, showing how used each window it refills is. A redeemed Codex reset moves the account's weekly refresh to a week from then; a Claude one keeps the weekly reset day. Once redeemed, an account cooling down from a used-up window rejoins its pool at once (a short rate limit still runs out), and its windows and resets are read again. A redeem the provider refuses (nothing to refill yet, its wait between resets, no longer available) spends nothing and says why. When no answer comes back, the daemon asks once more as the same redeem, then says the outcome is unknown, and the list shows whether it went through. A disabled account may redeem; one that needs sign-in may not. When Codex offers an account an instant reset to buy, its sheet links to Codex's purchase page.

Neither provider documents these endpoints: the daemon calls the ones their own clients call, and its Claude calls name Claude Code's user agent, which Claude lists limit resets only to. If either changes, the account shows no limit resets and keeps serving.

## Prices

Prices come from a snapshot of [models.dev](https://models.dev) in `apps/cli/src/usage/price-table.ts`; the daemon never fetches them. Run `bun apps/cli/scripts/update-prices.ts` to refresh it.
